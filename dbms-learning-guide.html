01 / Mental model

What is a DBMS?

A Database Management System is software that stores, protects, searches, and changes data. PostgreSQL is your DBMS. TypeORM is the application library that helps NestJS talk to PostgreSQL.

In your project

Application layer

Services such as FeeTemplatesService describe business operations. Repositories turn those operations into SQL.

The database layer

Data guarantees

Primary keys, unique constraints, foreign keys, indexes, and transactions protect data even when many requests arrive together.

One sentence to remember: application code says what the business wants; the DBMS makes storage, lookup, relationships, and consistency reliable.
02 / Structure

Tables, rows, columns, and keys

A table stores one kind of thing. A row is one instance. A column is one property. A key identifies a row or connects it to another table.

Primary key

A value that uniquely identifies each row. Your entities commonly use generated UUIDs.

id uuid PRIMARY KEY

Example: Project.id

Foreign key

A column that points to a row in another table. It expresses a relationship and prevents references to missing parents.

project_members.projectId -> projects.id

Example: ProjectMember.project

Unique constraint

Prevents duplicate business values. Your project prevents duplicate project codes within a tenant.

UNIQUE (tenantId, code)

Example: Project @Unique

NULL

NULL means “unknown or not supplied.” It is not the same as an empty string or zero. Nullable foreign keys are useful for optional relationships.

departmentId uuid NULL

Example: a user may have no department yet.

03 / Relationships

How tables connect

Relationships describe how many rows on one side can connect to rows on the other side.

One-to-one

One row matches at most one row. Example: one UserInfo record has one authentication record through authId.

user_info
1 : 1
auth_users

One-to-many

One parent has many children. A project can have many tasks; each task belongs to one project.

projects
1 : many
tasks

Many-to-many

Many users can belong to many projects. A junction table turns this into two one-to-many relationships.

users
1 : many
project_members
many : 1
projects

Self-reference

A table can point back to itself. A task can have a parent task, creating a hierarchy.

tasks.parentTaskId -> tasks.id
Why not store all project users in one column?

That creates repeating data, makes joins harder, and makes uniqueness and foreign-key validation weaker. project_members gives every membership its own row.

04 / Data quality

Normalization

Normalization is a method for reducing duplicate facts and update bugs. It is not “split every table until it is tiny.” Split data when one fact has its own identity or repeats.

1NF: atomic values

Each cell should hold one value, not a list. project_members follows this. memberIds uuid[] is a deliberate exception.

2NF: whole-key dependency

Every non-key value must depend on the whole key. Junction tables with a composite uniqueness rule are a common example.

3NF: no transitive dependency

A non-key column should not depend on another non-key column. Keep department details in departments, not repeated in every user row.

Your practical verdict

Most live entities are roughly 3NF. Arrays, JSONB, and cached totals are denormalization choices. The risk is having two sources of truth, such as project membership arrays plus project_members.

05 / Speed

Indexes

An index is a lookup structure. It makes reads faster by avoiding a full scan, but it consumes space and makes writes slightly more expensive.

B-tree: your default

Good for equality, joins, ranges, uniqueness, and sorting.

WHERE tenantId = ?
ORDER BY createdAt DESC

Composite indexes

Column order matters. Because your SaaS queries commonly filter by tenant first, (tenantId, projectId) is sensible.

Examples: Task indexes

GIN / trigram: not currently standard

Use GIN for JSONB or arrays, and trigram GIN for LIKE '%text%' search. These are next-step indexes, not the default for every column.

How to prove an index helps

Use PostgreSQL's query plan rather than guessing.

EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;
Index warning: more indexes are not always better

Every INSERT, UPDATE, or DELETE may need to update each relevant index. Add an index for a real query pattern, then verify it with a plan.

06 / Daily SQL

The SQL you will use constantly

Most real application work is selecting, filtering, joining, grouping, and safely changing rows. Learn the shape of the query before memorizing every keyword.

Read: choose columns, table, then conditions.

SELECT id, title
FROM tasks
WHERE tenant_id = $1
  AND is_deleted = false
ORDER BY created_at DESC
LIMIT 20;

Write: change only the rows you intend to change.

UPDATE tasks
SET status_id = $1, updated_at = now()
WHERE id = $2
  AND tenant_id = $3;
Habit: inspect the WHERE clause before running an update or delete.

Aggregate: turn many rows into a summary.

SELECT status_id, count(*)
FROM tasks
WHERE tenant_id = $1
GROUP BY status_id;

WHERE filters rows before grouping; HAVING filters groups after grouping.

NULL: use IS NULL, not = NULL.

WHERE deleted_at IS NULL
WHERE department_id IS NOT NULL

07 / Design discipline

Constraints, cascades, and data ownership

Application validation improves user experience. Database constraints are the final guardrail when another code path, script, or concurrent request writes data.

NOT NULL

Use when a fact is required. A booking's exam type should not silently disappear.

CHECK

Use for values such as non-negative amounts or valid state combinations.

CHECK (amount >= 0)

ON DELETE

CASCADE removes dependent rows, SET NULL preserves history, and RESTRICT blocks deletion.

Your project members use cascade when a project is deleted.

Source of truth

Decide where a fact lives. If membership is in project_members, do not independently maintain membership arrays without a clear synchronization rule.

Choose a policy

There is no universally correct option. The business meaning decides.

08 / Safety

Transactions and ACID

A transaction groups related database changes into one unit. Your services use TypeORM transactions when a business operation writes multiple related rows.

A

Atomicity: all changes happen, or none happen.

Strongly used in your code.

C

Consistency: constraints and business rules remain valid.

Supported by constraints plus atomic writes.

I

Isolation: concurrent work should not interfere incorrectly.

Mostly default PostgreSQL behavior.

D

Durability: committed data survives a crash.

Provided by PostgreSQL after commit.

Real example: question tree

Create/update can touch the question, options, answers, and child questions. The QueryRunner commits only after all work succeeds.

startTransaction()
save question + children + options
commitTransaction()
rollbackTransaction() on error

Open questions.service.ts

Gap to remember: exam booking result update and candidate Japanese-level update happen as separate saves in the live code. If they must never diverge, they belong in one transaction.
09 / Reading data

Joins

A join combines rows from related tables. The join type answers: should rows without a match still appear?

INNER JOIN

Only matching rows. Your candidate ownership check uses this because a candidate must have a tenant-owned batch.

candidate INNER JOIN batch
WHERE batch.tenantId = ?

LEFT JOIN

Keep every row from the left table, even when the right side is missing. Useful when listing achievements that may not have a related target.

RIGHT JOIN

Keep every row from the right table. It is valid SQL but rarely needed because the same query is usually clearer with the table order reversed.

JOIN warning

Joining a one-to-many relation can duplicate parent rows. Use grouping, distinct selection, or load the relation intentionally.

SELECT candidate.*
FROM candidate_profiles candidate
INNER JOIN batches batch ON batch.id = candidate.batch_id
WHERE candidate.id = $1 AND batch.tenant_id = $2;

Application example: candidate-access.service.ts

10 / Production thinking

Concurrency, security, and reliability

A database is used by many requests at once and must survive mistakes, crashes, and growth. These concepts turn “it works locally” into dependable software.

Concurrency

Two requests can read the same value and both try to change it. Transactions, locks, unique constraints, and optimistic version checks prevent lost updates.

Isolation levels

PostgreSQL commonly starts at Read Committed. Stronger isolation reduces anomalies but can increase retries and conflicts.

Security

Use least-privilege database roles, parameterized queries, secret management, and tenant enforcement. TypeORM parameters help prevent SQL injection; authorization still belongs in the application/database policy.

Reliability

Backups, restore drills, migrations, monitoring, slow-query logs, and connection-pool limits matter as much as table design.

12 / The focused 20%

Specialist topics for specific situations

Do not start here. These concepts matter when traffic, data size, compliance, or architecture demands them.

Views and materialized views

Saved query definitions; materialized views store a refreshable result for reporting.

Stored functions and triggers

Logic inside PostgreSQL. Powerful for universal rules, but hidden side effects can make application behavior harder to trace.

Partitioning

Split one logical table into physical pieces, often by date or tenant, when tables become very large.

Replication and read replicas

Copy data to other servers for availability or read scale. Replicas may lag behind the primary.

Sharding

Distribute data across independent database nodes. It adds routing and operational complexity; do it only when one database cannot scale.

OLTP versus OLAP

OLTP handles small, concurrent business writes. OLAP handles large analytical scans. Reporting often deserves a separate model.

Full-text and vector search

PostgreSQL can support text search and extensions. Use them for search workloads, not as a replacement for normal relational predicates.

Distributed systems

Eventual consistency, idempotency, queues, outbox patterns, and sagas appear when one transaction cannot cover multiple services.

A practical learning order

  1. Foundation: rows, keys, constraints, relationships, normalization, and basic SQL.
  2. Daily engineering: joins, indexes, transactions, pagination, validation, and migrations.
  3. Production: concurrency, tenant security, backups, monitoring, query plans, and failure recovery.
  4. Specialist: replication, partitioning, sharding, analytical models, and distributed consistency.
