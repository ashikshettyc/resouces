A

Multi-tenancy

sheets 01–05

NAVISHR runs one codebase and one database for every customer ("tenant") — Wipro's data and Infosys's data sit in the same tables. Everything in this category exists to answer one question correctly, every single time: whose request is this, and is it only touching what it's allowed to touch?

Subdomain resolution

01 / 19

Think of the platform as one large office building. Every tenant gets their own floor. The subdomain — wipro.navishr.com — is what's printed on the directory board in the lobby: it tells the elevator which floor to send you to before you've shown any ID.

On every incoming request, middleware reads the hostname, strips the shared base domain (navishr.com), and treats whatever's left as the tenant's slug. A handful of names — www, api, admin, system — are reserved and never resolve to a real tenant, so the marketing site or the bare API host can never accidentally be treated as someone's floor.

common/middleware/tenant.middleware.ts
common/utils/subdomain.util.ts — the extraction + reserved-name logic

The x-tenant-id override

02 / 19

A subdomain is the door number you walked up to. x-tenant-id is a master keycard — it opens a specific floor regardless of which door you're standing at, which is exactly what a building superintendent (Super Admin) needs.

Once logged in, the frontend itself sends this header on every request — the tenant ID from the logged-in user's session always wins over re-deriving it from the URL. The same header is also how a Super Admin impersonates a tenant to debug an issue without logging in as that org.

Where
common/middleware/tenant.middleware.ts:15-22 — header wins over subdomain
NAVISHR-Dashboard/src/http/httpClient.ts:36-40 — frontend attaching it

Tenant boundary enforcement

03 / 19

Even with a keycard, a good front desk double-checks the badge photo matches the floor you're requesting. Resolving a tenant is not the same as being allowed into it.

A non-Super-Admin who sends an x-tenant-id that doesn't match the tenant baked into their own JWT gets an immediate 403 — before any permission logic even runs. This closes the obvious hole where the header-override convenience from sheet 02 could otherwise be used by any logged-in user to peek at another tenant's data.

Where
common/guards/permissions.guard.ts:74-84

Row-level isolation

04 / 19

Picture a librarian who, no matter what title you ask for, only ever hands you a book stamped with your own library card's branch code — versus a librarian who hands you whatever's on the shelf and trusts you to check the stamp yourself before reading it.

The second librarian is what a raw TypeORM repository is: nothing stops a service from writing repo.findOne({ where: { id } }) and forgetting tenantId entirely — and that's already happened once in this codebase. TenantScopedRepository is the first librarian: it wraps the repository so every read merges tenantId into the query automatically, and every write stamps it on the way in. There's no method on the wrapper that can build a query without it.

Rollout status Not every module has been migrated to the scoped repository yet — see your pms-tenant-audit-progress notes: Placement and Tasks-attachments are done, Performance is paused pending a rebuild, Assessment is waiting on another team.
Where
common/repositories/tenant-scoped.repository.ts

Tenant suspension

05 / 19

A company ID badge that's deactivated at security the instant HR suspends someone — not one that quietly still works until the next time they happen to clock in.

tenant.active is checked on every authenticated request, inside the JWT validation step itself — not just at login. The moment a Super Admin suspends an org, its users' next API call anywhere in the app gets a 401 with a specific message, which the frontend recognizes and turns into an immediate, forced logout rather than trying (and failing) to silently refresh the token.

Where
auth/jwt.strategy.ts:40-44 — the check, on every request
NAVISHR-Dashboard/src/http/httpClient.ts:107-114 — the frontend reacting to it
B

AuthN / AuthZ

sheets 06–09

Authentication ("who are you") and authorization ("what are you allowed to do") are two different jobs that get confused constantly. NAVISHR keeps them as two separate stages a request passes through, in a fixed order, so a fix to one can never accidentally weaken the other.

JWT access + refresh tokens

06 / 19

The access token is a festival wristband: the gate stamps it once, and every other checkpoint inside can verify it just by looking — nobody needs to call the ticket office back. It's cheap to check but deliberately short-lived. The refresh token is your ticket stub: worthless for getting past a checkpoint, but exchangeable at the office for a brand new wristband without buying a new ticket.

Login returns both. Every request after that carries the access token in Authorization: Bearer …. When it expires, the axios client doesn't bother the user — it silently trades the refresh token for a new access token, replays the failed request, and even queues any other requests that failed at the same moment so they don't all race to refresh independently.

Where
auth/jwt.strategy.ts, auth/jwt-auth.guard.ts
NAVISHR-Dashboard/src/http/httpClient.ts:116-129 — the request queue during refresh
Read nextjwt.io — Introduction to JSON Web Tokens · Auth0 — Refresh Token Rotation

RBAC + per-user overrides

07 / 19

Your job title hands you a default toolbox — that's Role-Based Access Control. A manager who hands you one extra tool, or takes one away, without changing your title on the org chart, is the per-user override layered on top.

Each user has a role, and each role has a list of permissions (strings like tasks:task:create). UserPermissionService then computes that user's effective permissions — role permissions plus or minus any individual grants/revokes — once per login, and that computed list rides inside the JWT payload so every later request checks it without hitting the database again.

Where
auth/jwt.strategy.ts:46-52 — effective permissions computed at login
common/guards/permissions.guard.ts, common/decorators/permissions.decorator.ts — @Permissions('tasks:task:create')
Read nextNIST — Role-Based Access Control

Tenant module gating

08 / 19

A cable package. Your household plan might not include the sports channel at all — it doesn't matter that you, personally, know how to work the remote. RBAC decides what a role can do; module gating decides what a tenant has even paid for.

Each tenant carries a modules flag set — taskManager, placement, performance, assessment, and so on. The permission guard maps a required permission's namespace (placement:…, tasks:…) to the module it belongs to, and rejects the request outright if that module is explicitly switched off — even for a role that would otherwise be granted it. A module that's simply undefined (added after a tenant was created) defaults to allowed, specifically so shipping a new module never silently breaks an existing tenant.

Where
tenant/entities/tenant.entity.ts:9-30 — the TenantModules shape
common/guards/permissions.guard.ts:23-111 — the gate itself
Read nextMartin Fowler — Feature Toggles

Super Admin / the system tenant

09 / 19

The building superintendent isn't a resident of any one floor — they carry a master key that works everywhere, precisely because their job is managing the building, not living in an apartment.

Super Admins live in a special system tenant, bypass the ordinary permission checks entirely, and are the only ones exempt from the tenant boundary check in sheet 03 — that's how impersonation via x-tenant-id is allowed at all. Platform-only actions (creating tenants, suspending one) go through a separate guard, since there's no single tenant to scope those to.

Where
common/guards/super-admin.guard.ts
auth/jwt.strategy.ts:59 — isSystemTenant flag
C

Observability

sheets 10–12

When something goes wrong in production, you weren't standing there watching it happen — the logs are the only witness. This category is about making sure that witness can actually answer "what happened to this specific request," not just "something happened, at some point, to someone."

Trace / correlation ID

10 / 19

A claim-check ticket, stapled invisibly to your coat as it passes through the cloakroom, the tailor, and back to the front desk. Nobody carrying your coat had to be told its ticket number by hand — it just travels with the coat. If you call back later with a complaint, that ticket number is how every department finds their own notes about your coat, and only your coat.

Node's AsyncLocalStorage is that invisible staple. Middleware generates a UUID (or reuses an incoming x-request-id) at the very start of the request and opens a storage context around everything that follows. Every controller, service, and repository call downstream is still running inside that context — so the logger can read the trace ID back out at any point, without a single function signature anywhere having to accept and pass a traceId parameter. It's also echoed back to the caller as an x-correlation-id response header.

Where
common/middleware/correlation-id.middleware.ts
common/services/request-context.service.ts — the AsyncLocalStorage wrapper
common/configs/logger.config.ts:12-18 — Winston pulling it into every log line
Read nextNode.js docs — AsyncLocalStorage · Microsoft REST API Guidelines — Correlation IDs

Structured logging + redaction

11 / 19

A log book kept in a consistent shorthand instead of free-hand prose, so a machine can search it as reliably as a person can read it — with a censor's marker blacking out anything sensitive before the page ever gets filed away.

Winston writes JSON lines to daily-rotated files (14 days retained, gzipped), and a custom formatter walks every log object recursively, replacing any key named password, token, secret, authorization, cookie, or otp with [REDACTED] — so a stray console.log-style dump of a request body can't leak a credential into a file that outlives the incident it was written for.

Where
common/configs/logger.config.ts

Request logging interceptor

12 / 19

The doorman's logbook: who came in, when, how long they stayed, and whether they left through the front door or got escorted out.

A NestJS interceptor wraps every handler and logs method, path, status code, IP, user agent, and latency on the way out — success or failure — independent of the file-based Winston transport in sheet 11. It's the fast, always-on pulse check; the daily log files are the deep archive.

API plumbing

sheets 13–16

The parts of the API that have nothing to do with tasks, placements, or performance reviews — the shape every response takes no matter which of those it's carrying, so the frontend only has to learn that shape once.

Exception filters → the response envelope

13–14 / 19

No matter what breaks in the kitchen — wrong order, dropped plate, oven fire — the front desk always hands the customer back the same shaped comment card. The customer never sees the kitchen's chaos, just a consistent, predictable form.

Whatever happens inside a handler — a validation error, a permission denial, a database constraint, a Multer file-too-large error, or a plain unexpected exception — a global filter normalizes all of it into one ApiError shape before it leaves the server, hiding stack traces outside development. On the happy path, an interceptor does the mirror-image job: it wraps whatever the handler returned into the same envelope. Either way, the client always receives { success, statusCode, message, data }, and axios on the frontend unwraps it once, centrally, so every component just sees clean data.

Where
common/filters/all-exceptions.filter.ts, common/filters/database-exception.filter.ts
common/interceptors/transform.interceptor.ts
main.ts:52-57 — both registered globally

DTO validation pipe

15 / 19

A bouncer with an actual guest list, not a vibe check. If your name (a field) isn't on the list, you don't get in — and everyone on the list gets their ID checked and converted into the expected format on the way through the door.

Every incoming body/query is validated against a DTO class decorated with class-validator rules. whitelist: true strips any field that isn't declared on the DTO; forbidNonWhitelisted: true goes further and rejects the whole request if one shows up; transform: true converts primitives (a query string "5" becomes the number 5) before your handler ever sees them.

Where
main.ts:34-43

Swagger, Helmet & CORS

16 / 19

Three unrelated jobs that every production API needs, bundled here because they're all one-line concerns set up once in main.ts: Swagger auto-generates a browsable API directory at /api straight from the DTOs and decorators already in the code, so it can't drift out of date the way a hand-written doc can. Helmet sets a batch of security-relevant HTTP response headers by default (the safety signage bolted onto every floor). CORS is the policy for which other websites' JavaScript is allowed to call this API from a browser at all — here it's opened wide (origin: true) because the dashboard is served from many tenant subdomains that can't be enumerated as a fixed allow-list.

main.ts:21-31, 60-68

Storage

sheet 17

Presigned S3 URLs

17 / 19

Instead of an office clerk personally walking every visitor down to the storage vault and back, they hand the visitor a temporary keycard — good for one specific locker, for one hour — and let the visitor go there directly themselves.

Uploads and downloads of private files never stream through the NestJS server's own memory or bandwidth. The backend asks S3 to mint a presigned URL: a normal S3 URL with a cryptographic signature and expiry baked into the query string, proving the holder was authorized by someone who has the real credentials — without those credentials ever leaving the server. The browser then talks to S3 directly. Even the one deliberately unauthenticated upload path (a candidate's exam-registration photo) still re-derives trust from the request's tenant subdomain rather than accepting a raw tenant ID from the client.

Domain pattern

sheet 18

Freeze / lock

18 / 19

A notarized, sealed document — once stamped, nobody can quietly edit page three later. Reopening it requires someone with actual authority to break the seal on purpose.

A generic helper for records that need to become immutable once they're "done" — think a finalized performance review or a closed reconciliation. It supports an explicit manual freeze, and an automatic one that kicks in N days after a record's completedAt date, with unfreezing gated as an admin-only action. It's a small, boring service, but it's the kind of thing that protects audit trails from a well-meaning "oops let me just fix that one number" edit six months later.

common/freeze/freeze.service.ts
G

Frontend

sheet 19

Axios interceptor chain

19 / 19

A mailroom clerk who stamps every outgoing envelope with your return address and ID before it leaves the building, and who opens and sanity-checks every incoming reply before it lands on your desk — quietly renewing your ID badge and re-sending anything that bounced for that reason, without ever making you walk down to the mailroom yourself.

This is the one piece of the puzzle that lives entirely in the browser, but it's what makes sheets 02, 06, and 14 invisible to the rest of the app. A request interceptor attaches the bearer token and the tenant headers from sheets 01–02 to every outgoing call. A response interceptor unwraps the envelope from sheet 14, and on a 401 runs the refresh flow from sheet 06 — including queuing any requests that failed while a refresh was already in flight, so a page with five simultaneous API calls doesn't trigger five separate refresh attempts.

Suggested order

If you're starting from zero

The nineteen sheets are grouped by topic above, but topic order isn't learning order. This is the order that builds on itself with the least backtracking.

  1. How one HTTP request becomes a response — skim sheets 13 & 14 first. Everything else in this document is something that happens during that one round trip, so it helps to see the whole trip once before zooming into any one stop.
  2. Prove who's asking — sheet 06 (JWT). This is the most transferable concept here; it shows up in nearly every modern web app, not just this one.
  3. Decide what they can do — sheets 07, 08, 09 in order. RBAC first, then the tenant-level module gate stacked on top of it, then the platform-level Super Admin escape hatch.
  4. Figure out whose data it even is — sheets 01 through 05. This is the most NAVISHR-specific cluster; almost nothing here generalizes to a single-tenant app, so it rewards reading last, once request/auth basics feel familiar.
  5. Watch it happen after the fact — sheets 10, 11, 12 (tracing and logging), then 17 (storage) and 18 (freeze) as smaller, self-contained side quests.
  6. Close the loop on the frontend — sheet 19 ties 02, 06, and 14 back together from the browser's side.
